# Database

PostgreSQL through Drizzle ORM (a MongoDB flavour exists: see the last section). Locally the database is PGlite
(Postgres compiled to WASM, running inside the backend process, data in `backend/.data/`); anywhere else it is a real
Postgres named by `DATABASE_URL` (Supabase, Neon, RDS, self-hosted). The same migrations run on both. The current schema
as a diagram: [diagrams/database.md](diagrams/database.md) (generated from the Drizzle files by
`deno task --cwd backend diagrams`).

## Where things live

| What                                                                                | Where                                                                                   |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Accounts, sessions, organizations, members, invitations                             | `backend/src/shared/db/auth-schema.ts` (generated by Better Auth, never edited by hand) |
| Tables every project has: `audit_log`, `files`, `notifications`, `idempotency_keys` | `backend/src/shared/db/schema.ts`                                                       |
| Feature tables (`notes` is the worked example)                                      | `backend/src/modules/<feature>/schema.ts`                                               |
| Shared column helpers (`id()`, `createdAt()`, ...)                                  | `backend/src/shared/db/columns.ts`                                                      |
| Migrations (SQL, committed)                                                         | `backend/drizzle/`                                                                      |
| Fake development data                                                               | `backend/scripts/seed.ts`                                                               |

## Conventions

**Names.** Tables are plural `snake_case` (`notes`, `audit_log`), columns `snake_case`, TypeScript properties
`camelCase`. Foreign keys are `<thing>_id`. Indexes are named `<table>_<columns>_idx`. Booleans read as facts
(`enabled`, not `status_flag`).

**Ids are UUIDv7.** Time-ordered UUIDs generated in the application (`id()` helper) so that `ORDER BY id` is creation
order, inserts stay index-friendly, and a list cursor is just "the last id seen" (see keyset pagination in the API).
Better Auth's tables use `text` primary keys, filled with UUIDv7 strings by the same generator; our foreign keys to them
are `text`. Never expose sequential integers in URLs.

**Timestamps.** `timestamptz` always, stored in UTC. `created_at` on every table, `updated_at` where rows change
(`$onUpdate` keeps it current). Serialized as ISO 8601 strings in the API.

**Soft delete.** Default is hard delete. Use `deleted_at` only for content users may expect to restore or that other
rows reference in audits (`notes`, `files`). Every query on such a table filters `deleted_at IS NULL` inside its
repository; unique constraints on them need a partial index (`WHERE deleted_at IS NULL`). Personal data must still be
erasable: deleting an account removes the user's personal space and its content (see `user.deleteUser` in
`shared/auth/auth.ts`).

**Money.** Integer minor units (cents) in a `bigint`/`integer` column plus a 3-letter currency code in `text`. Never
`float`/`double`; `numeric` only when you must store fractions of a cent. Stripe is the source of truth for what was
charged; keep your copy to what you must query.

**Enums.** A Postgres enum (`pgEnum`) for a small closed set that rarely changes (`file_status`). For sets that grow or
are edited by operators, a lookup table or a `text` column with an application-side check. Adding an enum value is a
safe migration; removing or renaming one is not (see below).

**Constraints.** Put rules in the database as well as in code: `NOT NULL` by default, `UNIQUE` for natural keys, foreign
keys with an explicit `ON DELETE` (`cascade` for owned rows, `set null` for authorship), `CHECK` for ranges. The
contract validates input; constraints catch the bugs that get past it.

**Indexes.** Every foreign key you filter or join on, and every `(tenant, id)` pair behind a list endpoint
(`notes_org_idx` on `(organization_id, id)` serves "latest notes of an organization" without a sort). Add an index
because a query needs it, check with `EXPLAIN`, not by habit; each index slows writes.

## Multi-tenancy

Everything a customer owns carries `organization_id`. Users belong to organizations through `member` (role `owner`,
`admin` or `member`); every new user gets a personal organization, so features work for a solo user and a team alike.

Two layers keep tenants apart:

1. **Row checks in the application (always on).** A request resolves its tenant once (`requireTenant`: the
   `X-Organization-Id` header or the caller's personal organization, and the caller must be a member). Repository
   functions take `organizationId` as a parameter and put it in every `WHERE`, so a handler cannot forget it. The notes
   tests prove another tenant gets 404 and a forged header gets 403.
2. **PostgreSQL row-level security (optional defence in depth).** For stricter isolation, enable RLS on tenant tables,
   `SET LOCAL app.organization_id = '<id>'` at the start of each request transaction and add a policy
   `USING (organization_id = current_setting('app.organization_id'))`. It needs a non-superuser connection role and
   transaction-per-request, so it is not enabled by default.

## Migrations (drizzle-kit)

Edit a schema file, then:

```
deno task --cwd backend db:generate --name add_widgets   # writes backend/drizzle/NNNN_add_widgets.sql
deno task --cwd backend diagrams                          # refreshes docs/diagrams/database.md
```

Review the SQL, commit it with the schema change. Migrations apply automatically when the backend starts (and in tests,
on a throwaway in-memory database), so a schema change is never half-deployed. Never edit a migration that has been
applied anywhere; add a new one. `deno task --cwd backend check` fails if the diagram is stale. When Better Auth plugins
change (a module adds two-factor, for instance) run `deno task --cwd backend db:auth-schema` first, then `db:generate`.

### Zero-downtime rules

The old version of the code keeps running while the migration applies, and for a moment the new code runs on the old
schema. So each migration must work with both, and risky changes are split into several deploys:

- **Add** a column as nullable or with a constant default; backfill in batches; then add `NOT NULL` in a later migration
  (`ADD CONSTRAINT ... NOT VALID`, then `VALIDATE CONSTRAINT`, avoids a long lock).
- **Rename or retype** with expand and contract: add the new column, write to both, backfill, switch reads, stop writing
  the old one, drop it in a later release. Never `RENAME COLUMN` in one deploy.
- **Drop** a column or table only after no running code reads it.
- **Indexes** on a live table: `CREATE INDEX CONCURRENTLY` (it cannot run inside a transaction: put it alone in its own
  migration file and mark the statement breakpoint accordingly).
- **Enums:** only add values. To remove one, migrate to a new type.
- Keep migrations short; long backfills belong in a job (jobs module), not in a migration.
- Test the migration on a copy of production data before a risky release.

## Seeding

`deno task --cwd backend seed` creates fake people (`ada@example.com`, `ben@...`, `chloe@...`, password `password1234`),
a shared organization "Acme Notes" with 12 notes, a pending invitation, a notification and audit rows. It is idempotent
and refuses to run when `APP_ENV=production`. Extend `scripts/seed.ts` as you add features so a new developer sees a
realistic app in one command.

## Backups and restore

PGlite data is disposable development data: delete `backend/.data/` to reset.

For real Postgres: use the provider's automated daily backups and point-in-time recovery (Supabase, Neon and RDS all
offer it; check the plan includes it), and take a logical backup before risky migrations:

```
pg_dump --format=custom --no-owner "$DATABASE_URL" > backup-$(date +%F).dump
pg_restore --no-owner --dbname "$TARGET_URL" backup-YYYY-MM-DD.dump
```

A backup you have not restored is a hope. Rehearse a restore into a scratch database each quarter and write down how
long it took. Store dumps encrypted and outside the database provider's account.

## Local versus production

|                 | Local / tests                     | Production                                                                                 |
| --------------- | --------------------------------- | ------------------------------------------------------------------------------------------ |
| Engine          | PGlite (Postgres 17 in WASM)      | Postgres 15+                                                                               |
| Connection      | none; `PGLITE_DIR` or `memory://` | `DATABASE_URL` (use the pooler URL on serverless hosts)                                    |
| Migrations      | applied at start                  | applied at start of the first instance; roll out one instance first if a migration is slow |
| Background jobs | in-process queue                  | pg-boss on the same database (jobs module)                                                 |
| Extensions      | what PGlite bundles               | whatever the provider allows                                                               |

Differences are small, but before relying on a Postgres-only feature (RLS, an extension) and before a release, start the
backend against an empty real Postgres (`DATABASE_URL=... deno task --cwd backend start`, then `GET /ready`) in CI so
the migrations run on the engine you ship on. The test suite itself always uses PGlite.

## MongoDB flavour

A project created with `--db mongodb` swaps the PostgreSQL layer for MongoDB through Mongoose (same API, same contract,
same tests). Everything above about ids, tenancy, soft delete and money still applies; this section is what changes.
Pick it when your data is document-shaped (variable fields, deeply nested content) and you do not need relational
constraints or SQL-only features. Modules that need SQL (`requires.db: "postgres"` in their manifest: admin, audit,
flags, jobs, payments, push, search, storage) cannot be added to a MongoDB project; the generator refuses them.

The seam: services and routes do not know the database. Each feature has a `repository.ts` with the same function names
in both flavours, and the database-specific pieces of the base live in `backend/src/shared/db/` (`client.ts`,
`membership.ts`, `auth-adapter.ts`, `idempotency-store.ts`) and are replaced wholesale by the flavour.

| What                                                           | Where                                                                                                                                  |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Collections, fields, indexes (Mongoose)                        | `backend/src/shared/db/models.ts`                                                                                                      |
| Users, sessions, accounts, organizations, members, invitations | Better Auth's MongoDB adapter (`@better-auth/mongo-adapter`); the models describe those documents for queries, indexes and the diagram |
| Migrations                                                     | `backend/migrations/NNNN_name.ts` (`deno task --cwd backend migrate`; also run at start)                                               |
| Fake development data                                          | `backend/scripts/seed.ts`                                                                                                              |
| Collections diagram                                            | [diagrams/database.md](diagrams/database.md), generated from the models by `deno task --cwd backend diagrams`                          |

**Modelling.** One collection per entity, `_id` a UUIDv7 string (so `_id` order is creation order and the keyset cursor
is the last `_id`, exactly as in SQL). Reference other documents by id (`organizationId`, `authorId`) and look them up;
embed only small, bounded data that is always read with its parent (a note's tags, an address). Unbounded lists
(comments, events) get their own collection. Money: integer minor units plus a currency code, never a double. MongoDB
does not enforce references, so deleting something means deleting or detaching what points at it in code
(`removeOrphanedSpaces` is the worked example for account deletion).

**Multi-tenancy.** Same rule: every tenant-owned document has `organizationId`, every repository function takes it and
puts it in the filter, and tenants resolve once per request (`requireTenant`). MongoDB has no row-level security; the
filter is the isolation, so keep it in repositories and covered by tests (the notes tests prove it).

**Indexes.** Declared next to the fields in `models.ts` and created by migrations, not at runtime (`autoIndex` is off,
because index builds on a large live collection must be deliberate). Order compound indexes equality fields first, then
sort, then range (`{ organizationId: 1, _id: -1 }` serves "latest notes of an organization"). Unique indexes carry the
rules a foreign key or `UNIQUE` carries in SQL (`member` is unique per organization and user). TTL indexes expire rows
by themselves (idempotency keys after 24 hours, sessions and verification tokens at their `expiresAt`), so there is no
cleanup job. Check queries with `explain("executionStats")`.

**Soft delete.** Same policy: `deletedAt` on content people may restore (`notes`, `files`), filtered in the repository.

**Transactions.** Single-document writes are atomic, so model data so one operation changes one document where you can.
Multi-document transactions need a replica set (Atlas always is; a plain local `mongod` is not): use
`connection.transaction(async (session) => ...)` where several documents must change together, and run staging on a
replica set. The shipped code avoids them: operations are ordered and idempotent, so a retry repairs a partial failure.

**Migrations.** MongoDB has no schema to diff, so migrations are explicit: add `migrations/0002_what.ts` exporting
`up(db)` (create or change indexes with `Model.createIndexes()` or `syncIndexes()`, backfill or reshape documents in
batches). Applied names are recorded in `_migrations`; each runs once, in name order, at start (two instances may race,
so migrations must be idempotent). The expand-and-contract rules above apply to field renames and removals as well:
write both shapes, backfill, switch reads, then clean up. If you prefer a dedicated tool, migrate-mongo works with the
same layout; the shipped runner is about twenty lines and needs no extra dependency.

**Backups.** Atlas: continuous cloud backup with point-in-time restore. Self-hosted: a replica set with scheduled
`mongodump --uri "$MONGODB_URI" --gzip --archive=backup-$(date +%F).gz`, restored with
`mongorestore --uri "$TARGET_URI" --gzip --archive=backup-YYYY-MM-DD.gz --drop` into a scratch database. As with SQL, a
backup you have not restored is a hope: rehearse it. Store archives encrypted and outside the database's account.

**Local development and tests.** No MongoDB install: `mongodb-memory-server` starts a real `mongod` for you. The first
run downloads the server binary (several hundred MB, cached afterwards; set `MONGOMS_VERSION` to pick a version) and
keeps local data in `backend/.data/mongo`; tests use a throwaway in-memory instance per test file. To use your own
server instead, set `MONGODB_URI` (for example the Docker service below): the app uses it, and tests create and drop a
uniquely named database there.

```yaml
# compose.dev.yaml (optional: MongoDB in Docker instead of the managed binary)
services:
  mongo:
    image: mongo:8
    ports: ["27017:27017"]
    volumes: [mongo-data:/data/db]
volumes: { mongo-data: {} }
```

Then `MONGODB_URI=mongodb://localhost:27017/app`. (The managed binary is exercised by the test suite; the Compose file
is standard but was not run here.) Production: `MONGODB_URI` pointing at Atlas or your cluster, with a user limited to
the application database. Without a URI the backend starts the managed binary, so in production always set it.

|                                                | PostgreSQL flavour                            | MongoDB flavour                          |
| ---------------------------------------------- | --------------------------------------------- | ---------------------------------------- |
| Local engine                                   | PGlite                                        | managed `mongod` (mongodb-memory-server) |
| Connection variable                            | `DATABASE_URL`                                | `MONGODB_URI`                            |
| Schema source                                  | Drizzle files, SQL migrations (`db:generate`) | Mongoose models, `migrations/*.ts`       |
| Referential integrity                          | foreign keys, cascades                        | application code                         |
| Jobs, search, payments tables, audit, flags... | modules available                             | SQL-only modules not available           |
